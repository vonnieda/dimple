⏺ Refactoring Detail Pages to New Controller Pattern

  Here's a comprehensive todo list for converting other detail pages (like genre_details.rs, release_details.rs, etc.) to the new controller pattern we implemented for
  artist_details.rs:

  1. Convert old-style detail pages to new controller pattern

  - Replace function-based approach with struct-based controllers
  - Follow the same pattern as ArtistDetailsController

  2. Create MutableStringParam for dynamic query parameters

  - Use MutableStringParam instead of String for the current key/ID
  - Import from crate::ui::common::MutableStringParam
  - Allows efficient parameter updates without recreating subscriptions

  3. Replace manual notification observers with QuerySubscriptions

  - Remove app.library.notifier.observe() calls
  - Replace with app.library.db.query_subscribe() for reactive data updates
  - Much more efficient and targeted than global notifications

  4. Move subscription creation to controller constructor

  - Create all QuerySubscriptions once in the new() method
  - Store subscriptions as fields in the controller struct
  - Use MutableStringParam as query parameter for all subscriptions

  5. Use proper reference tables (GenreRef, LinkRef, ArtistRef) in SQL queries

  - Genres: JOIN GenreRef gr ON g.id = gr.genre_id WHERE gr.model_id = ?
  - Links: JOIN LinkRef lr ON l.id = lr.link_id WHERE lr.model_id = ?
  - Artists/Releases: JOIN ArtistRef ar ON ar.model_id = r.id WHERE ar.artist_id = ?
  - Never query direct foreign keys - always use the reference tables

  6. Add controller to App struct for navigation access

  - Add controller field to App struct: Arc<RwLock<ControllerType>>
  - Initialize in AppWindowController::new()
  - Allows access from navigation functions

  7. Update navigation function to use controller

  - Modify navigate function in App::navigate() to get controller with write().unwrap()
  - Pass controller to detail function: detail_function(&url, self, &mut controller)
  - Update function signature to accept &mut Controller

  8. Remove old init functions that set up manual observers

  - Remove calls to *_details_init() functions from AppWindowController::run()
  - Delete the old init functions entirely
  - Controller constructor now handles all setup

  Key Benefits of This Pattern:

  - Performance: Subscriptions created once, reused efficiently
  - Consistency: All detail pages follow same pattern
  - Maintainability: Clear separation of concerns
  - Reactivity: Automatic UI updates when data changes
  - Memory efficiency: No subscription recreation overhead

  This pattern should be applied to genre_details.rs, release_details.rs, playlist_details.rs, and any other detail pages that currently use the old notification observer pattern.
